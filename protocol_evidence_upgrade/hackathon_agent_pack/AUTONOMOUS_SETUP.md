# Автономная подготовка, запуск и проверка

Это требования к действиям кодинг-агента в рабочем репозитории. Пакет содержит
спецификацию, а не уже установленное приложение. Установки и испытания нужно
действительно выполнить в среде пользователя и зафиксировать результат.

## 1. Разрешение пользователя и границы

Пользователь разрешает самостоятельно:
- использовать интернет для официальной документации, установки зависимостей,
  инструментов и скачивания доступных моделей и разрешённых тестовых материалов;
- создавать проектные виртуальные окружения, локальные конфигурации и каталоги;
- скачивать веса ASR, диаризации, текстовой LLM и опционального YOLO;
- поднимать локальные сервисы, выполнять миграции SQLite и проверять приложение;
- исправлять обнаруженные ошибки и повторять тесты.

Не спрашивай подтверждение на каждый пакет, скачивание весов или запуск тестов
в этих границах. Не заканчивай ответом «установите зависимости и запустите сами».
Отсутствие модели в начале — задача подготовки, а не окончательный блокер.

Это разрешение НЕ включает оплату, покупку вычислений, создание учётных записей,
обход ограничений доступа, угадывание паролей, получение чужих токенов, удаление
пользовательских файлов, изменение глобальных драйверов/GPU, глобального firewall
или публичную публикацию сервера. Не запускай неизвестные скрипты из случайных
источников. Используй официальные источники и проверяй происхождение команд.
Соблюдай доступные разрешения среды; не пытайся обходить её защиту.

При необходимости привилегий сначала ищи установку в пользовательский каталог
или другой совместимый способ. Пароли не вводи и не выводи. Gated-модели загружай
только при действительном доступе пользователя; не заявляй, что условия приняты,
если это не так. Если доступ отсутствует, проверь доступную локальную альтернативу.
Вопрос нужен только для действительно неразрешимого выбора/права; независимые
части при этом продолжай выполнять.

## 2. Два отдельных режима

BOOTSTRAP_ONLINE — разрешены скачивание кода, пакетов, весов, документации и
тестовых материалов с подходящей лицензией. Не загружай вовне аудио, видео,
транскрипты, контакты, секреты и результаты реальных совещаний.

RUN_OFFLINE — все модели уже локальные. Веб-интерфейс, ASR, диаризация, LLM,
экспорт и дополнительные функции работают без исходящих внешних соединений.
Не подменяй локальный inference облачным API, не скачивай веса лениво при
загрузке записи. При необходимости новой модели останавливай обработку и
запускай отдельный этап подготовки, затем повторяй локальную проверку.

Обращения внутри локальной машины, например к локальному LLM-сервису, допустимы.
Проверка офлайн-режима должна сохранять эти локальные соединения.

## 3. Подготовь среду сам

1. Осмотри репозиторий и инструкции. Проверь ОС, архитектуру, версии Python,
   CPU/GPU, RAM, доступную видеопамять и свободный диск. Не печатай значения
   секретов при диагностике переменных окружения.
2. Создай проектную .venv или используемую проектом эквивалентную среду. Версии
   выбирай по фактической совместимости, проверяя официальную документацию при
   необходимости. Не обновляй все пакеты без причины.
3. Установи backend, зависимости распознавания и диаризации, обработку аудио,
   экспорт и тестовые инструменты. Подготовь ffmpeg и доступный локальный
   LLM-runtime. Браузер для UI-тестов устанавливай доступным разрешённым способом.
4. При конфликте ASR/диаризации изолируй их в отдельных средах или процессах.
   Не ломай системный Python и существующие пользовательские сервисы.
5. Подготовь .env с реальными путями и безопасными локальными значениями.
   .env.example не содержит токенов. Зафиксируй проверенные версии зависимостей.
6. Запусти doctor и короткие проверки загрузки каждого компонента. Успешный
   импорт Python-пакета не равен успешной загрузке модели и inference.

## 4. Скачай и проверь модели

Сначала инвентаризируй кэш: переиспользуй совместимые полные файлы. Проверь
оценочный размер скачиваний и запас диска, не загружай несколько больших
вариантов без необходимости. Загружай минимальную достаточную конфигурацию.
Сохраняй прогресс и возобновляй загрузку, если инструмент это поддерживает.

ASR: используй многоязычную модель Whisper через faster-whisper, не English-only.
Выбирай размер и вычислительный режим по фактическим ресурсам. Упрощённый профиль
допустим только с честной фиксацией влияния на качество, особенно казахской речи.

Диаризация: попробуй pyannote community-1 при наличии законного доступа. Если
нужного доступа нет, исследуй и внедри доступную локальную альтернативу настоящей
диаризации. Сохрани общий контракт. Не подменяй её VAD, чередованием голосов по
строкам, ручной разметкой или заранее известным числом участников.

LLM: подними локальный runtime, например Ollama, и скачай подходящую текстовую
многоязычную модель. При выборе нового тега проверь его наличие и требования в
официальной документации, а не придумывай имя. Выполни настоящий тест генерации
и валидации структуры поручений. Не используй cloud-теги или удалённый endpoint.

YOLO: веса скачивай только если основной сценарий уже работает и модуль камеры
реализуется. Сначала реальная детекция на разрешённом тестовом изображении/видео,
затем интеграция. Учти лицензию конкретных кода и весов.

Для каждой модели проверь полный набор файлов: веса, tokenizer, конфигурации,
зависимые модели. Подготовка не завершена, пока модель не загружена из локального
пути и не выполнен пробный inference без дополнительного скачивания.

Создай models/manifest.json с model_id, источником, ревизией/digest, лицензией,
локальным путём, профилем устройства/квантования и результатом smoke-test.
Записывай только фактически проверенные значения. Хеш файла помогает проверять
целостность повторной сборки, но сам по себе не доказывает надёжность источника.
Веса не включай в Git или архив исходного кода.

## 5. Самостоятельно подними сервисы

Запусти локальный LLM-сервис, backend и необходимые worker-процессы. Не стартуй
дубликаты уже работающих совместимых сервисов. Проверь их реальный статус,
HTTP-ответы и хотя бы один запрос к каждому ML-компоненту.

Привязывай сервисы к loopback. Если порт занят, не убивай чужой процесс: выбери
другой локальный порт и обнови согласованную конфигурацию. Логи храни локально,
без токенов и полного текста реальных совещаний. Сохрани PID только собственных
процессов; команда stop не должна завершать процессы пользователя.

UI должен открываться и использовать тот backend, который действительно запущен.
Проверь загрузку записи, polling статуса, ошибки и экспорт через интерфейс,
не ограничивайся curl /api/health. Запуск приложения без моделей отмечай как
неполную готовность, а не успешное развёртывание.

## 6. Подготовь данные и проверь сквозной сценарий

Сначала зафиксируй ожидаемые результаты независимо от вывода моделей. Не меняй
эталон на ошибочный результат ради зелёного теста. Не ослабляй проверки и не
добавляй обходной путь для известного имени тестового файла.

Если пользовательских записей нет, самостоятельно подготовь безопасные тесты:
локально синтезированные вымышленные диалоги и/или разрешённые тестовые записи с
подходящей лицензией. Не привлекай внешний speech API. Для казахского проверь
поддержку языка выбранным локальным синтезатором или используй доступные
лицензированные записи. Не называй неподтверждённую озвучку казахским эталоном.

Создай tests/data/manifest.json: источник, лицензия, язык, длительность,
число голосов и признак synthetic. Для тестов диаризации нужны отличимые голоса,
а не один голос с разной громкостью. Зафиксируй ограничения синтеза.

Подай фактический аудиофайл через обычный upload и весь REAL-процесс:
ASR → диаризация → подтверждение участников → поручения → саммари → DOCX.
Для синтетического аудио модели работают по-настоящему, но вход явно помечается
как synthetic. Это не то же самое, что FIXTURE с готовым JSON.

Отдельно выполни:
- unit-тесты контрактов, дат, пустых реквизитов и ссылочной целостности;
- интеграционные тесты локальных ASR, диаризации и LLM;
- E2E на русском, казахском и смешанной речи с несколькими голосами;
- случаи согласованного и отклонённого переноса, «вчера уже сделал», пустых
  реквизитов, «я подготовлю» и явно названного другого исполнителя;
- текстовые отрицательные примеры и отсутствие новых поручений;
- ошибки пустого/повреждённого файла, недоступной модели/LLM, прерывания задания;
- UI-тест через доступный браузер: загрузка, просмотр, правка, утверждение,
  переход по основанию и скачивание DOCX;
- проверку DOCX: открытие, содержимое, версия, статус, казахские буквы;
- повторный запуск и сохранность данных;
- RUN_OFFLINE после отключения внешних соединений в разрешённой изолированной
  среде, включая браузер и локальный LLM.

Флаги offline без сетевой проверки не доказывают отсутствие внешнего трафика.
Если изоляция недоступна, проверку отсутствия внешних соединений пометь NOT RUN.
Не меняй глобальный firewall без отдельного разрешения. Сохраняй localhost.

Результаты на синтетической речи не доказывают качество настоящих совещаний.
Отчитайся отдельно: unit, integration, synthetic-audio E2E, natural-audio E2E,
UI, offline. При отсутствии естественных записей natural-audio E2E = NOT RUN.
Три примера не являются репрезентативным исследованием точности.

До правок секретаря измеряй автоматический результат отдельно от утверждённого.
Внешним кодинг-агентам и терминальному выводу, который они увидят, не раскрывай
реальные персональные данные: локальные проверки возвращают безопасные статусы.

## 7. Исправляй и повторяй

Рабочий цикл: запусти → воспроизведи ошибку → найди причину → исправь → повтори
тот же тест → повтори связанные проверки. Отчёт о падении не завершает задачу,
если ошибку можно исправить в разрешённых условиях.

При OOM сначала освобождай только свои модели, запускай тяжёлые этапы
последовательно, используй совместимый меньший/квантованный профиль либо CPU.
Фиксируй выбранный режим; не называй его равноценным без измерений.
При отсутствии доступа к gated-весам попробуй доступный локальный компонент.
При нехватке места убирай только собственные временные файлы или выбери более
компактный профиль; пользовательские данные и чужой кэш не удаляй.

Не повторяй заведомо одинаковую неудачную команду бесконечно. После нескольких
осмысленных попыток используй совместимую альтернативу или укажи точный блокер,
сохрани результаты и заверши независимые части. Не скрывай недоступные функции
зелёным health-check. Бюджет спринта включает установку и скачивание.

## 8. Артефакты и завершение

Реализуй и действительно проверь простые команды/скрипты с такими функциями:
- bootstrap — идемпотентная установка и подготовка моделей с разрешённой сетью;
- doctor — проверка окружения, файлов моделей и сервисов без вывода секретов;
- run — запуск локального приложения без скачиваний;
- test — unit/integration/UI и отдельные ML-проверки;
- e2e — подача нового аудиофайла по настоящему пользовательскому пути;
- verify-offline — разрешённая проверка сетевой автономности;
- stop — завершение только собственных сервисов.

Конкретную форму выбирай по ОС (Python-скрипт, shell, PowerShell или Makefile).
Не заявляй универсальность, если проверена лишь одна платформа. В README запиши
точные выполненные команды, версии, ревизии моделей, оборудование и лицензии.

Создай:
- reports/test-results.json и читаемый TEST_REPORT.md с PASS/FAIL/NOT RUN;
- reports/environment.json без секретов;
- models/manifest.json и tests/data/manifest.json;
- безопасные логи, результаты тестов, скриншоты UI и демонстрационный DOCX,
  когда соответствующие проверки действительно выполнены;
- README с разделением BOOTSTRAP_ONLINE и RUN_OFFLINE, командами и ограничениями.

В финале сообщи: что установлено и скачано; какие сервисы действительно работают;
какие команды и тесты реально выполнены; адрес интерфейса; какие требования не
выполнены. Не выдавай список желаемых команд за журнал исполнения.

Если среда не удерживает сервер между вызовами, честно укажи это и оставь
проверенную команду повторного запуска. Не обещай работу после завершения сессии.
Не объявляй обязательный сценарий готовым при сломанной диаризации или языке.
